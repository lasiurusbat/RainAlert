# RainAlert implementation plan

Status as of 2026-10-22. Checked items (`[x]`) are finished and can be seen in
the repository. Unchecked items (`[ ]`) are open. Items marked **(verify)** may
already be done, but nothing in the repository proves it, so they stay open
until confirmed.

Live site: <https://rainalert.live> — **planned, not live.** Image:
`lasiurusbat/rainalert` (repository exists, no tags). Repository:
<https://github.com/lasiurusbat/RainAlert>.

## 1. Where we are

The app works locally, is containerised, has a CI/CD pipeline and Dependabot
committed and pushed to GitHub, and has a deployment runbook. No release tag
exists yet, no image has been pushed, and the domain answers nothing, so
**the app is local-only** — it reaches nobody who is not already looking at
the page. Tier 1 of the alert ideas is complete: the page colour-codes rain
risk, shows an hour-by-hour strip for today with a "bring an umbrella"
summary, leads with a one-line headline, and renames the browser tab and
swaps the favicon when rain is coming. Tier 2 is also built: the reader's
city and their own rain threshold live in the browser's `localStorage`, the
site stays stateless, a browser notification says so when rain is about to
start while the tab is open, and the app is installable: it ships a web
manifest and a service worker, so it can be added to a home screen and opens
without a network. The site is also built to be found: every city has one
address of its own, there is a city index, a sitemap and a robots file, and
a page that is missing says so with its status code.

## 5. Alert features

Order follows the ideas document. Tier 1 and 2 need no database and no new
costs. Tier 3 is the step that makes the app a real alert service.

### Tier 1: in-page (all done)
- [x] Headline banner above the list ("Rain likely tomorrow (80%). Bring an umbrella." / "No rain likely for the next 7 days."). Built in `forecast_headline()`. The band name in the sentence is the day's own band, the same one its row in the list carries, so the banner and the list never disagree. Today is judged on the hours that are left, not on the daily maximum, and the sentence says which figure it is using ("Rain likely for the rest of today (80%)"); a day that is over drops out, and a missing chance is never counted as dry.
- [x] Hour-by-hour strip for today using Open-Meteo hourly precipitation: 24 bars for the city's local day, colour-coded on the same severity bands as the daily list, with a one-line summary ("Rain likely from about 15:00 to 18:00, up to 83%. Bring an umbrella.")
- [x] Tab title and favicon change when rain is coming. Built in `tab_alert()`, which fires at the same `UMBRELLA_THRESHOLD` as the ☔ icon and the banner, so the tab, the banner and the row can never disagree. The title names the day ("Rain tomorrow - Rain Alert") rather than the date, today is judged on the hours that are left exactly as the banner judges it, and the two favicons are separate files because browsers cache a favicon by its URL.

### Tier 2: browser-side (all done)
- [x] Remember city and threshold in `localStorage`, check on page load. Built in `static/app.js`. Both preferences live in the browser and the server stays stateless; the server only tells the page what kind of page it is through `data-autoload`, `data-search` and `data-city` on `<body>`. A city is only remembered once a search for it has actually worked (the submitted city waits in `sessionStorage` until the result page confirms it), so a typo is never remembered and a failed search does not destroy the saved city. The threshold is marked with its own symbol and its own words, because it answers a different question from the umbrella, and it is compared against the number the page shows so the two can never disagree. Without JavaScript the preferences row is hidden.
- [x] Web Notifications while the tab is open. Built as a 🔔 button next to the hourly strip's title, plus a poll of `/api/alert` every 30 minutes. The decision and the wording live on the server, in `notification_event()` in `app.py`, so they are covered by the offline test suite; the browser only asks and shows. Each event carries a key and the browser remembers the keys it has shown, so the same news is never said twice. The reader's own threshold is used when they have set one, and the notification says so; without one it is the app's own umbrella threshold, so the notification is the same alert as the ☔ icon, not a second one. It only works while the tab is open, and the Notification API needs a secure context, so the button says "Notifications blocked" rather than offering something that cannot work.
- [x] Installable PWA: manifest, service worker, icons. Built as `static/manifest.json` and `static/service-worker.js`, served from the **root** (`/manifest.json`, `/service-worker.js`) so the scope covers the whole site, with four generated PNG icons (180, 192, 512 and a maskable 512) and an `apple-touch-icon`. The worker follows two rules: the forecast is never cached (navigations are network-first with the browser's own cache bypassed, `/api/` and `/calendar.ics` are never intercepted, and `/` is absent from the shell list), and the shell is cached so an installed app opens without a network and shows an honest offline page instead of a stale forecast. Bumping `CACHE_VERSION` in the worker is how a changed shell reaches readers. It still cannot push to a closed app — that is Tier 3.
- [x] Calendar export (`.ics`) for rainy days. Built as a quiet "📅 Add rainy days to my calendar" link on the caption line beside "7-day rain chance", which downloads a standard iCalendar file from `/calendar.ics` with one all-day event for every day that reaches the threshold. The file is built by `build_calendar()` in `app.py`, so the rule that decides which days go into it is behind the offline test suite; the browser only says which threshold the reader is using, and takes the link away when nothing reaches it. The reader's own threshold is used when they have set one, and the app's umbrella threshold when they have not — the same split as the ▲ marker and the notification. The events are all-day events, because the forecast is a daily maximum, and their ids are derived from the city and the date, so importing the file again updates the same events instead of adding duplicates. A day the service did not report is never in the file. The link sits on the caption line because the card is at its vertical limit: it costs 0px.

### Tier 3: server-pushed alerts
Decide first, because it affects hosting and licensing:
- [ ] Choose the channel to start with (suggestion: ntfy.sh or Telegram, because no signup flow is needed)
- [ ] Decide storage: the free Render filesystem is wiped on restart, so subscriptions need external storage
- [ ] Decide the scheduler: GitHub Actions on a schedule (free) rather than inside the sleeping web service
- [ ] Store latitude, longitude and timezone at signup so scheduled runs do not re-geocode
- [ ] Change detection ("tomorrow went from 20% to 75%") instead of fixed-time spam
- [ ] Check Open-Meteo limits: scheduled checks add calls, and limits apply per IP address (shared runner IPs can hit them sooner)
- [ ] Licence check: free alerts are fine under the non-commercial terms; a paid tier is not (needs a paid Open-Meteo plan)

## 7. Deferred or out of scope

- Display ads (AdSense) and affiliate links: need an Open-Meteo commercial plan, ad-network approval, a consent tool for EEA/UK/Swiss visitors and policy pages. The ideas doc does not cover this, so the analysis behind the decision above lives in the decision record, not there.
- Paid alert tier or sponsorship: same licence requirement, plus accounts, payments and support.
- Cloud Run hosting: set aside because of the card requirement and custom-domain costs.
